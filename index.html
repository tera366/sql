SQL Complete Guide: Fundamentals to Interview Level

This guide covers every topic in the requested list with explanations, syntax, examples, interview notes, and common pitfalls. Examples use mostly standard SQL; exact syntax can differ between SQL Server, MySQL, PostgreSQL, Oracle, and other databases.

Important: LIMIT, DATE_ADD, MONTHS_BETWEEN, and some date functions are database-specific. SQL Server commonly uses TOP/OFFSET FETCH, while PostgreSQL/MySQL use LIMIT.

1. SELECT, WHERE, ORDER BY

SELECT

SELECT chooses columns or expressions to return.

SELECT name, salary
FROM employees;

Return all columns:

SELECT * FROM employees;

WHERE

WHERE filters rows before grouping and aggregation.

SELECT name, salary
FROM employees
WHERE salary > 50000;

ORDER BY

ORDER BY sorts the final result. Default is ascending.

SELECT name, salary
FROM employees
ORDER BY salary DESC;

Multiple columns:

SELECT name, department_id, salary
FROM employees
ORDER BY department_id ASC, salary DESC;
Interview point: WHERE filters rows; ORDER BY sorts the result. An alias can generally be used in ORDER BY, but not in WHERE at the same query level.

2. DISTINCT

DISTINCT removes duplicate result rows.

SELECT DISTINCT department_id
FROM employees;

With multiple columns, uniqueness is based on the combination:

SELECT DISTINCT department_id, job_title
FROM employees;
DISTINCT does not mean “find duplicate records.” It removes duplicates from the returned result.

3. LIMIT

LIMIT restricts the number of rows returned in MySQL/PostgreSQL.

SELECT *
FROM employees
ORDER BY salary DESC
LIMIT 5;

Top 5 is meaningful only with a deterministic ordering. SQL Server uses TOP (5) or OFFSET ... FETCH.

4. CASE WHEN

CASE implements conditional logic and returns a value.

SELECT name, salary,
       CASE
         WHEN salary >= 100000 THEN 'High'
         WHEN salary >= 60000 THEN 'Medium'
         ELSE 'Low'
       END AS salary_band
FROM employees;

Simple CASE:

SELECT name,
       CASE department_id
         WHEN 10 THEN 'IT'
         WHEN 20 THEN 'HR'
         ELSE 'Other'
       END AS department_name
FROM employees;
CASE is commonly used for categorization, conditional aggregation, custom sorting, and conditional calculations.

5. NULL Handling

NULL means missing/unknown value. It is not equal to zero, an empty string, or a normal value.

Correct:

SELECT *
FROM employees
WHERE manager_id IS NULL;

Incorrect:

-- Wrong
WHERE manager_id = NULL;

For non-NULL:

WHERE manager_id IS NOT NULL;
Three-valued logic: comparisons involving NULL generally produce UNKNOWN. WHERE keeps only TRUE rows.

6. COALESCE and NULLIF

COALESCE

Returns the first non-NULL expression.

SELECT name,
       COALESCE(phone, email, 'No contact') AS contact
FROM customers;

NULLIF

Returns NULL when two expressions are equal; otherwise returns the first expression.

SELECT NULLIF(discount, 0) AS discount
FROM products;

A common division-by-zero pattern:

SELECT sales / NULLIF(quantity, 0) AS average_price
FROM orders;

8. Date and Time Functions

Date syntax varies substantially by database.

DATE_ADD

-- MySQL style
SELECT DATE_ADD(order_date, INTERVAL 7 DAY)
FROM orders;

DATE_SUB

-- MySQL style
SELECT DATE_SUB(order_date, INTERVAL 30 DAY)
FROM orders;

DATEDIFF

-- MySQL-style example
SELECT DATEDIFF(end_date, start_date) AS days_taken
FROM projects;

MONTHS_BETWEEN

-- Oracle style
SELECT MONTHS_BETWEEN(end_date, start_date)
FROM contracts;

YEAR, MONTH, DAY

SELECT YEAR(order_date) AS order_year,
       MONTH(order_date) AS order_month,
       DAY(order_date) AS order_day
FROM orders;

DATE_TRUNC

Truncates a timestamp/date to a requested boundary in databases that support it, such as PostgreSQL.

SELECT DATE_TRUNC('month', order_date) AS month_start
FROM orders;
Interview tip: know the concept—adding/subtracting intervals, finding date differences, extracting date parts, and grouping dates—not just one vendor's syntax.

9. Type Casting

Converts one data type to another.

SELECT CAST(salary AS DECIMAL(12,2))
FROM employees;

Some systems also support:

SELECT CAST(order_date AS DATE)
FROM orders;

SQL Server additionally has CONVERT() and TRY_CAST().

11. LIKE, IN, BETWEEN

LIKE

SELECT *
FROM employees
WHERE name LIKE 'A%';

% means zero or more characters; _ means exactly one character.

IN

SELECT *
FROM employees
WHERE department_id IN (10, 20, 30);

BETWEEN

SELECT *
FROM employees
WHERE salary BETWEEN 50000 AND 80000;
BETWEEN is inclusive at both ends in standard SQL comparisons.

12. EXISTS / NOT EXISTS

EXISTS checks whether a correlated or uncorrelated subquery returns at least one row.

SELECT c.customer_id, c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);

This returns customers who have at least one order.

SELECT c.customer_id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);

This returns customers with no matching order.

EXISTS is especially useful when you only care whether a related row exists, not how many rows exist.

13. INNER JOIN

Returns only rows having matching values on both sides.

SELECT e.name, d.department_name
FROM employees e
INNER JOIN departments d
  ON d.department_id = e.department_id;

14. LEFT JOIN

Returns every row from the left table plus matching rows from the right. No match gives NULL for right-side columns.

SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id;

Find customers with no orders:

SELECT c.name
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

15. RIGHT JOIN

Returns every row from the right table plus matching rows from the left.

SELECT e.name, d.department_name
FROM employees e
RIGHT JOIN departments d
  ON d.department_id = e.department_id;
A RIGHT JOIN can usually be rewritten as a LEFT JOIN by swapping table positions. Many teams prefer LEFT JOIN for readability.

16. FULL OUTER JOIN

Returns matching rows plus unmatched rows from both tables.

SELECT e.name, d.department_name
FROM employees e
FULL OUTER JOIN departments d
  ON d.department_id = e.department_id;

17. CROSS JOIN

Produces the Cartesian product: every row from table A combined with every row from table B.

SELECT c.color, s.size
FROM colors c
CROSS JOIN sizes s;

If A has 5 rows and B has 4 rows, the result has 20 rows.

18. Self Join

A table is joined to itself, often for employee-manager or hierarchical relationships.

SELECT e.name AS employee,
       m.name AS manager
FROM employees e
LEFT JOIN employees m
  ON e.manager_id = m.emp_id;

19. GROUP BY

GROUP BY combines rows into groups so aggregate functions can calculate one result per group.

SELECT department_id, COUNT(*) AS employee_count
FROM employees
GROUP BY department_id;

Multiple grouping columns:

SELECT department_id, job_title, COUNT(*) AS cnt
FROM employees
GROUP BY department_id, job_title;

20. HAVING

HAVING filters groups after aggregation.

SELECT department_id, COUNT(*) AS employee_count
FROM employees
GROUP BY department_id
HAVING COUNT(*) > 5;
Remember: WHERE filters rows before GROUP BY; HAVING filters groups after GROUP BY.

21. COUNT

COUNT(*) counts rows. COUNT(column) counts non-NULL values. COUNT(DISTINCT column) counts unique non-NULL values.

SELECT COUNT(*) AS rows,
       COUNT(phone) AS phones,
       COUNT(DISTINCT department_id) AS departments
FROM employees;

22. SUM

SELECT customer_id, SUM(amount) AS total_spend
FROM orders
GROUP BY customer_id;

SUM normally ignores NULL values, though an all-NULL input can produce NULL depending on context/database behavior.

23. AVG

SELECT department_id, AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id;

AVG generally ignores NULL values in the input column.

24. MIN / MAX

SELECT department_id,
       MIN(salary) AS minimum_salary,
       MAX(salary) AS maximum_salary
FROM employees
GROUP BY department_id;

25. Window Functions Overview

Window functions calculate across related rows without collapsing them into one row per group.

General structure:

function(...) OVER (
    PARTITION BY ...
    ORDER BY ...
)

PARTITION BY defines the group/window. ORDER BY defines the sequence inside that window.

26. ROW_NUMBER()

Assigns a unique sequential number within each partition.

SELECT name, department_id, salary,
       ROW_NUMBER() OVER (
         PARTITION BY department_id
         ORDER BY salary DESC
       ) AS rn
FROM employees;

If two employees have equal salary, ROW_NUMBER still gives different numbers, so add a tie-breaker when deterministic ordering matters:

ORDER BY salary DESC, emp_id ASC

27. RANK()

Equal values receive the same rank, and gaps appear after ties.

SELECT name, salary,
       RANK() OVER (ORDER BY salary DESC) AS rnk
FROM employees;

Example salaries 100, 100, 90 produce ranks 1, 1, 3.

28. DENSE_RANK()

Equal values receive the same rank, but no gaps occur.

SELECT name, salary,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS dr
FROM employees;

Example salaries 100, 100, 90 produce ranks 1, 1, 2.

29. LAG()

Returns a value from a previous row in the window.

SELECT order_date, amount,
       LAG(amount) OVER (ORDER BY order_date) AS previous_amount
FROM orders;

Useful for comparing current vs previous transaction, salary, sale, or event.

30. LEAD()

Returns a value from a following row.

SELECT order_date, amount,
       LEAD(amount) OVER (ORDER BY order_date) AS next_amount
FROM orders;

31. FIRST_VALUE()

Returns the first value according to the window ordering.

SELECT department_id, name, salary,
       FIRST_VALUE(name) OVER (
         PARTITION BY department_id
         ORDER BY salary DESC
       ) AS highest_paid_employee
FROM employees;

32. LAST_VALUE()

Returns the last value according to the window frame. This is a common interview trap because the default frame in some databases may not mean “last row of the entire partition.” Explicitly specify the frame when needed.

SELECT department_id, name, salary,
       LAST_VALUE(name) OVER (
         PARTITION BY department_id
         ORDER BY salary
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS last_employee
FROM employees;

33. PARTITION BY

PARTITION BY divides rows into independent windows.

ROW_NUMBER() OVER (
    PARTITION BY department_id
    ORDER BY salary DESC
)

Ranking restarts at 1 for every department.

34. ORDER BY in Window Functions

The ORDER BY inside OVER controls calculation sequence. It is different from the final query's ORDER BY.

SELECT name, salary,
       LAG(salary) OVER (ORDER BY salary) AS previous_salary
FROM employees
ORDER BY name;

The window calculation is based on salary order, while the displayed result is sorted by name.

35. CTE

A Common Table Expression gives a temporary named result for one statement.

WITH dept_salary AS (
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id
)
SELECT *
FROM dept_salary
WHERE avg_salary > 70000;

CTEs improve readability and can be recursive.

36. Subqueries

A subquery is a query nested inside another query.

Scalar subquery

SELECT name, salary
FROM employees
WHERE salary > (
    SELECT AVG(salary) FROM employees
);

IN subquery

SELECT *
FROM employees
WHERE department_id IN (
    SELECT department_id
    FROM departments
    WHERE location = 'Hyderabad'
);

Correlated subquery

SELECT e.name, e.salary
FROM employees e
WHERE e.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e2.department_id = e.department_id
);

37. UNION

Combines result sets and removes duplicate rows.

SELECT email FROM customers
UNION
SELECT email FROM leads;

Both SELECT statements must have compatible column counts and types.

38. UNION ALL

Combines result sets while keeping duplicates.

SELECT email FROM customers
UNION ALL
SELECT email FROM leads;
UNION ALL is usually preferable when you do not need duplicate elimination because it avoids that extra distinct operation.

39. INTERSECT

Returns rows appearing in both result sets.

SELECT customer_id FROM online_customers
INTERSECT
SELECT customer_id FROM store_customers;

40. EXCEPT

Returns rows from the first result set that are not present in the second.

SELECT customer_id FROM customers
EXCEPT
SELECT customer_id FROM orders;

This can identify customers who have never ordered, subject to NULL/type and database-specific set-operation behavior.

41. SQL Query Execution Order

A useful logical processing order is:

  1. FROM
  2. JOIN / ON
  3. WHERE
  4. GROUP BY
  5. HAVING
  6. SELECT
  7. DISTINCT
  8. ORDER BY
  9. LIMIT / OFFSET or equivalent
SELECT department_id, COUNT(*) AS cnt
FROM employees
WHERE salary > 50000
GROUP BY department_id
HAVING COUNT(*) > 2
ORDER BY cnt DESC;

Conceptually, SQL first identifies source rows, joins them, filters rows, groups them, filters groups, calculates the SELECT list, removes duplicates if requested, sorts, and finally limits the output.

This is logical processing order, not a promise of the physical execution plan used by the database optimizer.

42. Performance Techniques

1. Indexing

Index columns frequently used for selective WHERE predicates, joins, and sometimes ORDER BY/GROUP BY. Avoid blindly indexing every column because indexes consume storage and make writes more expensive.

CREATE INDEX idx_orders_customer
ON orders(customer_id);

2. Avoid SELECT *

-- Prefer
SELECT customer_id, name
FROM customers;

3. Filter early when appropriate

Use selective predicates to reduce rows that need to be processed, while relying on the optimizer to transform queries when possible.

4. Avoid functions on indexed filter columns when they prevent index use

-- Often less index-friendly
WHERE YEAR(order_date) = 2026

-- Often better as a range
WHERE order_date >= '2026-01-01'
  AND order_date < '2027-01-01'

5. Use EXISTS when existence is all you need

Do not create large intermediate results merely to test whether a matching row exists.

6. Use UNION ALL when duplicate removal is unnecessary

7. Avoid unnecessary DISTINCT

DISTINCT may require sorting or hashing.

8. Inspect execution plans

Use your database's EXPLAIN/EXPLAIN ANALYZE or graphical execution plan tools.

9. Avoid accidental row multiplication

Joining one-to-many tables can multiply rows and inflate SUM/COUNT. Understand the cardinality before aggregating.

10. SARGability

A predicate is generally more index-friendly when the indexed column is compared directly to a value/range rather than transformed by a function.

Interview answer: Performance is not “always add indexes.” Start by measuring with an execution plan, identify scans, expensive joins, cardinality problems, sorts, spills, and poor estimates, then optimize the actual bottleneck.

43. Practical Combined Example

Find the top two highest-paid employees in each department, including only departments whose average salary is above 60,000.

WITH dept_avg AS (
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id
    HAVING AVG(salary) > 60000
),
ranked AS (
    SELECT e.name,
           e.department_id,
           e.salary,
           DENSE_RANK() OVER (
               PARTITION BY e.department_id
               ORDER BY e.salary DESC
           ) AS salary_rank
    FROM employees e
    INNER JOIN dept_avg d
      ON d.department_id = e.department_id
)
SELECT name, department_id, salary, salary_rank
FROM ranked
WHERE salary_rank <= 2
ORDER BY department_id, salary_rank;

This example combines CTE, JOIN, GROUP BY, HAVING, AVG, DENSE_RANK, PARTITION BY, ORDER BY, WHERE, and final ORDER BY.

44. Interview Questions and Answers

Q1. WHERE vs HAVING?

Answer: WHERE filters individual rows before grouping. HAVING filters groups after GROUP BY and can directly use aggregate expressions.

WHERE salary > 50000
HAVING AVG(salary) > 60000

Q2. COUNT(*) vs COUNT(column)?

Answer: COUNT(*) counts rows. COUNT(column) counts non-NULL values in that column.

Q3. COUNT(DISTINCT column)?

Answer: Counts unique non-NULL values.

Q4. Difference between RANK, DENSE_RANK and ROW_NUMBER?

Answer: ROW_NUMBER gives unique sequential numbers. RANK gives ties the same rank and leaves gaps. DENSE_RANK gives ties the same rank without gaps.

Q5. PARTITION BY vs GROUP BY?

Answer: GROUP BY collapses rows into groups. PARTITION BY creates windows while keeping individual rows.

Q6. Find the second-highest salary.

SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (
    SELECT MAX(salary) FROM employees
);

Or with DENSE_RANK:

WITH x AS (
  SELECT salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
)
SELECT salary
FROM x
WHERE rnk = 2;

Q7. Find the Nth-highest salary.

WITH x AS (
  SELECT salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
)
SELECT salary
FROM x
WHERE rnk = :N;

Q8. Find duplicate emails.

SELECT email, COUNT(*) AS cnt
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;

Q9. Return all rows containing duplicate emails.

SELECT *
FROM customers
WHERE email IN (
    SELECT email
    FROM customers
    GROUP BY email
    HAVING COUNT(*) > 1
);

Q10. Find customers with no orders.

SELECT c.*
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);

Q11. Find employees earning above their department average.

SELECT e.*
FROM employees e
WHERE e.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e2.department_id = e.department_id
);

Q12. Find highest-paid employee in each department.

WITH x AS (
  SELECT e.*,
         DENSE_RANK() OVER (
           PARTITION BY department_id
           ORDER BY salary DESC
         ) AS rnk
  FROM employees e
)
SELECT *
FROM x
WHERE rnk = 1;

Q13. Top 3 employees per department?

WITH x AS (
  SELECT e.*,
         ROW_NUMBER() OVER (
           PARTITION BY department_id
           ORDER BY salary DESC, emp_id
         ) AS rn
  FROM employees e
)
SELECT *
FROM x
WHERE rn <= 3;

If “top 3 salary levels” are required and ties should share the same rank, use DENSE_RANK instead.

Q14. Find each employee's previous salary.

SELECT emp_id, name, salary,
       LAG(salary) OVER (
         PARTITION BY department_id
         ORDER BY salary_change_date
       ) AS previous_salary
FROM employee_salary_history;

Q15. Find the difference from the previous row.

SELECT order_date, amount,
       amount - LAG(amount) OVER (ORDER BY order_date) AS difference
FROM orders;

Q16. INNER JOIN vs LEFT JOIN?

Answer: INNER JOIN returns only matching rows. LEFT JOIN returns all rows from the left table and matching right-side rows; unmatched right columns become NULL.

Q17. Why can a LEFT JOIN unexpectedly behave like an INNER JOIN?

-- Can remove unmatched rows:
SELECT c.*, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'PAID';

The WHERE condition rejects NULL order rows. If you need to preserve customers without paid orders, move the condition into ON:

LEFT JOIN orders o
  ON o.customer_id = c.customer_id
 AND o.status = 'PAID'

Q18. UNION vs UNION ALL?

Answer: UNION removes duplicate rows; UNION ALL keeps them and is generally cheaper when duplicate removal is unnecessary.

Q19. EXISTS vs IN?

Answer: Both can express membership/existence, and optimizers may transform them similarly. EXISTS is often natural for correlated existence checks. Be especially careful with NULL semantics when using NOT IN; NOT EXISTS is often safer for anti-joins.

Q20. NOT IN vs NOT EXISTS and NULL?

Answer: If the subquery used by NOT IN contains NULL, three-valued logic can cause surprising results. NOT EXISTS does not have that same NULL trap because it checks row existence.

Q21. What is a CTE?

Answer: A named temporary query result available to a single statement. It improves readability and can support recursive queries. It is not automatically a permanent table.

Q22. CTE vs temporary table?

Answer: A CTE is part of a statement's query expression. A temporary table is a database object with a temporary lifetime and can often be indexed or reused across multiple statements. Exact behavior depends on the database.

Q23. What is a correlated subquery?

Answer: A subquery that references a column from the outer query, so logically it is evaluated in relation to each outer row.

Q24. What is a self join?

Answer: Joining a table to itself using different aliases, commonly for employee-manager hierarchies or comparing rows in the same table.

Q25. What is a CROSS JOIN?

Answer: Cartesian product. Every left row is paired with every right row. If there are m and n rows, the result can contain m × n rows.

Q26. Why doesn't WHERE salary = NULL work?

Answer: NULL represents unknown/missing information, so equality comparison with NULL is UNKNOWN. Use IS NULL or IS NOT NULL.

Q27. COALESCE vs NULLIF?

Answer: COALESCE chooses the first non-NULL expression. NULLIF converts an expression to NULL when it equals another expression.

Q28. How do you avoid division by zero?

SELECT numerator / NULLIF(denominator, 0)
FROM metrics;

Q29. What is the logical SQL execution order?

Answer: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET, with details varying by dialect and constructs.

Q30. Why can't I use a SELECT alias in WHERE?

Answer: Logically WHERE is evaluated before SELECT, so the alias has not been produced at that logical stage. Use a subquery/CTE, or repeat the expression when appropriate.

Q31. Why can't I normally use a window-function alias in WHERE?

Answer: Window functions are evaluated after WHERE in the logical processing model. Put the window calculation in a CTE/subquery, then filter the outer query.

WITH x AS (
  SELECT e.*,
         ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn
  FROM employees e
)
SELECT *
FROM x
WHERE rn <= 3;

Q32. How do you find the second-highest distinct salary?

Answer: Use DENSE_RANK or MAX below MAX. DENSE_RANK handles duplicate salaries naturally.

Q33. How do you find duplicate records?

Answer: Identify the business key with GROUP BY and HAVING COUNT(*) > 1. Then join or use a subquery to retrieve full rows.

Q34. How do you delete duplicates while keeping one row?

WITH d AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY email
           ORDER BY customer_id
         ) AS rn
  FROM customers
)
DELETE FROM d
WHERE rn > 1;

Exact DELETE syntax for CTEs varies by database. Always test the SELECT version first and ensure the ordering identifies the row you intend to retain.

Q35. How do you calculate running total?

SELECT order_date, amount,
       SUM(amount) OVER (
         ORDER BY order_date
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM orders;

Q36. How do you calculate department total while keeping each employee row?

SELECT name, department_id, salary,
       SUM(salary) OVER (
         PARTITION BY department_id
       ) AS department_total
FROM employees;

Q37. What is a window frame?

Answer: It defines which rows around the current row are included in a window calculation. Common clauses include ROWS or RANGE with boundaries such as UNBOUNDED PRECEDING and CURRENT ROW.

Q38. Why can LAST_VALUE return an unexpected result?

Answer: Because the window frame may end at the current row rather than the last row of the full partition. Specify an appropriate frame when you need the final value across the entire partition.

Q39. What causes duplicate rows after a JOIN?

Answer: Usually a one-to-many or many-to-many relationship. One row on one side can match multiple rows on the other side. Before joining, understand primary keys, foreign keys, and relationship cardinality.

Q40. Why can COUNT(*) after a LEFT JOIN be surprising?

Answer: COUNT(*) counts the preserved left row even when the right side is unmatched. To count matching right-side records, count a non-NULL right-side key such as COUNT(o.order_id).

Q41. What is query SARGability?

Answer: It describes writing predicates in forms that allow the optimizer to efficiently use indexes. Applying a function to an indexed column can prevent efficient index seeking in some situations.

Q42. What should you check when a query is slow?

Answer: Start with the execution plan and actual measurements. Check table/index scans, expensive joins, poor cardinality estimates, large sorts/hashes, spills, missing or ineffective indexes, unnecessary columns, row multiplication, and blocking/locking where relevant.

Q43. WHERE vs ON in a JOIN?

Answer: ON defines matching between joined tables. WHERE filters the rows produced by the FROM/JOIN phase. With outer joins, moving a predicate between ON and WHERE can change the result.

Q44. Can aggregate functions be used in WHERE?

Answer: Not directly at the same query level because WHERE happens before GROUP BY aggregation. Use HAVING or a subquery/CTE.

Q45. Can aggregate functions be used in HAVING?

Answer: Yes. Example: HAVING COUNT(*) > 5.

Q46. GROUP BY vs DISTINCT?

Answer: DISTINCT removes duplicate result rows. GROUP BY creates groups and is designed for aggregation, although GROUP BY without aggregates can also produce unique combinations.

Q47. How do you find customers who placed more than three orders?

SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 3;

Q48. How do you find the latest order for every customer?

WITH x AS (
  SELECT o.*,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY order_date DESC, order_id DESC
         ) AS rn
  FROM orders o
)
SELECT *
FROM x
WHERE rn = 1;

Q49. How do you find customers with their first order date?

SELECT customer_id, MIN(order_date) AS first_order_date
FROM orders
GROUP BY customer_id;

Q50. How do you find employees whose salary is higher than their manager?

SELECT e.name AS employee,
       e.salary AS employee_salary,
       m.name AS manager,
       m.salary AS manager_salary
FROM employees e
JOIN employees m
  ON m.emp_id = e.manager_id
WHERE e.salary > m.salary;

47. Final Interview Strategy

  1. First understand the table grain: what does one row represent?
  2. Identify primary/foreign keys and relationship cardinality.
  3. Decide whether the problem needs filtering, aggregation, joining, or a window function.
  4. For “per department/customer/category” problems, immediately consider PARTITION BY or GROUP BY.
  5. For “top N per group,” consider ROW_NUMBER, RANK, or DENSE_RANK depending on tie requirements.
  6. For “no matching rows,” consider NOT EXISTS or LEFT JOIN ... IS NULL.
  7. For duplicates, GROUP BY + HAVING is the first pattern to recognize.
  8. For previous/next row comparisons, think LAG/LEAD.
  9. For multi-step logic, use a CTE to make each step clear.
  10. For performance questions, explain measurement and execution plans before recommending indexes.
Core patterns to memorize:
1. Duplicate detection → GROUP BY + HAVING COUNT(*) > 1
2. Top N per group → ROW_NUMBER/DENSE_RANK + CTE
3. Missing relationship → NOT EXISTS or LEFT JOIN + IS NULL
4. Previous row → LAG
5. Next row → LEAD
6. Conditional aggregation → SUM(CASE WHEN ... THEN 1 ELSE 0 END)
7. Above-average → aggregate subquery/CTE or window AVG
8. Latest row per entity → ROW_NUMBER() OVER(PARTITION BY ... ORDER BY date DESC)

End of guide. Always verify vendor-specific syntax against the database engine used in the interview or project.
